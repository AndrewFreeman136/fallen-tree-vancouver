Сохранённые исходники и резервная копия поэтому обязательны. Проверенный документ не гарантирует конкретное поведение проекта при каждом превышении. [Лимиты Pages](https://developers.cloudflare.com/pages/platform/limits/).

Запросы к статическим файлам бесплатны и не имеют счётного лимита, если не вызывают Functions. Pages Functions используют квоту Workers Free: суммарно 100 000 запросов в сутки на аккаунт, сброс в 00:00 UTC. Это не лимит просмотров статического сайта. Workers при исчерпании квоты возвращает ошибку 1027; конкретное поведение маршрута зависит от конфигурации. Поэтому обработчик формы нужно изолировать от страниц и показывать честную ошибку отправки. [Стоимость Pages](https://developers.cloudflare.com/pages/functions/pricing/), [лимиты Workers](https://developers.cloudflare.com/workers/platform/limits/).

Отдельно оплачивается продление домена у текущего регистратора. CA$36 + налоги взято только из переданного брифа, актуальная сумма и списание не проверены. Обработчик формы и будущая CMS ещё не выбраны: бесплатность хостинга не подтверждает бесплатность почты, хранилища оригиналов или редактора. ## Развёртывание и предпросмотр

1. После проверки копии владелица создаёт/выбирает контролируемые ею аккаунты Cloudflare и GitHub/GitLab. Исходники, структурированный контент и медиа сохраняются в её репозитории; чувствительных данных и старых заказов там быть не должно.
2. В Cloudflare открыть Workers & Pages → Create application → Pages → Connect to Git. Выбрать конкретный репозиторий, production-ветку, команду сборки и выходную папку из README. Для уже готового HTML сборка может быть пустой.
3. Проверить результат сборки на выданном `pages.dev`. Пуш в production-ветку автоматически обновляет сайт; другие разрешённые ветки дают preview. Выбор Git integration нельзя позже переключить в режим Direct Upload этого же проекта через интерфейс, хотя Wrangler-публикация возможна. Поэтому для будущего редактора предпочесть Git с самого начала. [Интеграция Git](https://developers.cloudflare.com/pages/get-started/git-integration/).
4. Тестирование вести через preview-ветку. Cloudflare по умолчанию добавляет таким preview `X-Robots-Tag: noindex`; сами адреса публичны. Для ограничения доступа включить политику Cloudflare Access и проверить её под чужой сессией. Эта настройка не защищает автоматически production `<project>.pages.dev` и собственные домены. До запуска отдельным правилом оставить production-копию без индексации; после запуска проверить удаление запрета только на production. [Preview и доступ](https://developers.cloudflare.com/pages/configuration/preview-deployments/).
5. До переключения проверить все URL, изображения, мобильные размеры, клавиатуру, FAQ, внешние ссылки и отсутствие зависимостей Squarespace. Если серверный обработчик заявки не подключён и не протестирован — оставить честный контакт email, без сообщения об успешной отправке.

## Домен, DNS и DNSSEC

Для корня `fallentreevancouver.com` Pages требует зону в том же аккаунте Cloudflare и Cloudflare nameservers. Для одного `www.fallentreevancouver.com` возможен CNAME на `<project>.pages.dev` при прежнем DNS-провайдере. Это не решает автоматически HTTPS/перенаправление корня. Рекомендуемый конечный вариант — оба адреса в Pages, DNS у Cloudflare, регистрация домена остаётся у Squarespace. Сначала добавить каждый адрес в Pages → Custom domains; одного самовольного CNAME недостаточно и возможна ошибка 522. [Собственные домены Pages](https://developers.cloudflare.com/pages/configuration/custom-domains/).

Порядок работы владельца после приёмки копии:

1. Экспортировать/сфотографировать все текущие DNS-записи, nameservers, состояние DNSSEC/DS и TTL. Сохранить A/AAAA/CNAME, MX, SPF/DKIM/DMARC, TXT проверки владения, CAA и поддомены. Записать оплаченный срок Squarespace и не отключать старый сайт.
2. Создать зону Cloudflare Free, перенести записи и сравнить каждую с исходной. Автосканирование Cloudflare не гарантирует полного переноса. Почтовые и проверочные записи сохранить с правильным режимом DNS only; DNS-провайдер не должен подменять существующий почтовый сервис. До запуска запланировать проверку почты. [Подключение полной зоны](https://developers.cloudflare.com/dns/zone-setups/full-setup/setup/).
3. Если DNSSEC включён, сначала удалить старый DS у регистратора/отключить DNSSEC по его инструкции. Дождаться полного истечения TTL старого DS и проверить отсутствие старого DS (`dig DS fallentreevancouver.com`). Не менять NS одновременно вслепую: закешированный старый DS с новыми ключами вызывает SERVFAIL. После истечения TTL заменить NS именно на два значения, назначенных этой зоне Cloudflare. После завершения делегирования включить DNSSEC в Cloudflare и внести новый DS в Squarespace. [Последовательность DNSSEC](https://developers.cloudflare.com/dns/dnssec/).
4. В Squarespace путь к NS: Domains → домен → DNS → Domain Nameservers → Use Custom Nameservers. Подтверждение входа выполняет владелица. Squarespace предупреждает о задержке до 48 часов и о том, что старые DNS-записи перестают применяться после перехода на чужие NS. Не полагаться только на мастер, который предлагает отключить DNSSEC в момент смены NS: выдержать предыдущий пункт заранее. [Инструкция Squarespace](https://support.squarespace.com/hc/en-us/articles/4404183898125-Review-change-or-reset-your-domain-s-nameservers).
5. Привязать оба имени в Pages, дождаться Active и действительного сертификата. Если есть CAA — проверить разрешение выпуска сертификата. Сохранить `https://www.fallentreevancouver.com` основным адресом, если аудит подтверждает его текущую каноничность; перенаправление с корня должно сохранять путь и query string. Проверить отсутствие циклов, canonical, sitemap и ссылки. Проверить HTTPS и обращения из нескольких сетей.

## Откат и завершение

Для ошибки в новой версии: Cloudflare Pages → Deployments → нужное ранее успешное production-развёртывание → меню → Rollback to this deployment. Preview не является допустимой целью отката. После экстренного отката также вернуть корректный контент в Git, иначе следующий пуш снова развернёт ошибочную версию. [Откат Pages](https://developers.cloudflare.com/pages/configuration/rollbacks/).

Для проблемы после первого переезда: пока Squarespace оплачен и сайт сохранён, восстановить его прежние A/AAAA/CNAME в действующей DNS-зоне по сохранённому снимку. Удалить конфликтующие записи; не угадывать IP. Если необходим возврат самих nameservers, это отдельный более медленный откат: сначала проверить DS и порядок DNSSEC, затем восстановить прежнее делегирование. При DNSSEC сначала удалить DS, дождаться TTL, сохраняя подпись зоны до истечения; прежние NS со старым несовместимым DS возвращать нельзя. [Откат DNSSEC](https://developers.cloudflare.com/dns/dnssec/).

DNS-откат не мгновенный из-за кешей. Возврат записи обратно в Pages также может потребовать повторной активации домена. После успешного переезда владелица отдельно прекращает подписку сайта Squarespace, сохраняя продление домена, аккаунт и необходимую историю заказов. Финальную инструкцию отмены и условия возврата перепроверить перед действием.

## Этап 2: редактор

Архитектурная основа: отдельные JSON/YAML/Markdown для страниц и работ; медиа в понятной папке; стабильные slug; поля `title`, `description`, `images`, `alt`, `order`, `published`, и уже существующая публичная цена при необходимости. Это ещё не административный интерфейс.

После завершения переноса проверить Decap CMS как кандидата поверх Git. В GitHub backend редактор входит GitHub-аккаунтом с правом push; требуется серверная OAuth-аутентификация либо отдельный провайдер. Git LFS этим backend не поддерживается. Значит, «CMS с открытым кодом» не равно автоматически «бесплатный вход и любые фотографии». [GitHub backend Decap](https://decapcms.org/docs/github-backend/).

Для рабочего прототипа включить черновики и отдельное действие публикации. В editorial workflow Decap сохраняет черновик в ветку/PR и сливает после публикации; привязать к нему preview Pages. [Редакционный процесс Decap](https://decapcms.org/docs/editorial-workflows/).

Критерий выбора и приёмки — Ирина с другого устройства самостоятельно проходит вход → меняет текст → загружает/переставляет фото → редактирует alt → просматривает черновик → публикует → видит результат на домене → откатывает изменение. Проверить потерю сессии, отказ сборки, конфликт одновременных правок, удаление/скрытие работы и восстановление резервной копии. Изменения должны сохраняться в репозитории, не только в браузере.

До обещания отсутствия подписки оценить по актуальным тарифам: авторизацию, права аккаунта, API-квоты, объём репозитория и фото, частоту сборок, хранение оригиналов, обслуживание обновлений. Сначала выбрать и проверить полный путь на аккаунтах владельца, потом фиксировать расходы и выдавать инструкцию. Управляемый Decap Turbo и иные облачные CMS пока не выбраны и бесплатными не заявляются.
